# Как войти на локальный сайт по сертификату

Инструкция для **Google Chrome на Ubuntu**. Названия кнопок приведены на английском, как в установленном браузере, с пояснениями на русском.

Один раз добавим в Chrome два файла: сертификат локального сайта и ваш личный сертификат для входа. После этого на сайте можно будет входить без логина и пароля.

Сначала выполните шаги 1–5. Команды Docker и техническое описание находятся в конце и для настройки браузера не нужны, если сайт уже запущен.

## Шаг 1. Найдите файлы сертификатов и скопируйте пароль

1. Откройте приложение **«Файлы»** в Ubuntu — значок папки на панели приложений.
2. Нажмите **Ctrl+L**, чтобы ввести путь к папке.
3. Скопируйте туда этот путь и нажмите **Enter**:

   ```text
   website-template/docker/traefik/certs/localhost
   ```

4. В папке найдите три файла:

   | Файл           | Для чего нужен                                               |
   | -------------- | ------------------------------------------------------------ |
   | `server.crt`   | Чтобы Chrome доверял нашему локальному сайту.                |
   | `client.p12`   | Ваш личный сертификат вместе с ключом для входа.             |
   | `p12-password` | Пароль, который Chrome попросит при добавлении `client.p12`. |

5. Нажмите правой кнопкой на **`p12-password`**, выберите **«Открыть с помощью…»**, затем текстовый редактор. Это обычный текстовый файл, хотя у него нет расширения `.txt`.
6. Скопируйте строку из файла целиком, без пробелов и переноса строки. Оставьте редактор открытым: пароль понадобится на шаге 3. Это пароль импорта файла, а не пароль вашей учётной записи на сайте.

Если папки или файлов нет, сначала нужно выполнить раздел **«Для разработчика: подготовка и запуск»** в конце инструкции.

## Шаг 2. Добавьте сертификат локального сайта в доверенные

1. Откройте **Google Chrome**.
2. Нажмите **Ctrl+L**, вставьте адрес ниже и нажмите **Enter**. Вставлять нужно именно в адресную строку браузера, а не в поиск на странице:

   ```text
   chrome://certificate-manager
   ```

3. Откроется **Certificate Manager** — управление сертификатами.
4. Слева выберите **Local certificates** — локальные сертификаты.
5. В разделе **Custom** нажмите **Installed by you** — установленные вами.
6. Найдите раздел **Trusted Certificates** — доверенные сертификаты. Нажмите **Import** именно в этом разделе. Ниже есть другие разделы с такими же кнопками — они здесь не нужны.
7. В окне выбора файла нажмите **Ctrl+L**, вставьте полный путь и нажмите **Enter**:

   ```text
   website-template/docker/traefik/certs/localhost/server.crt
   ```

8. Если окно выбора файла осталось открытым, нажмите **Open / Открыть**. Если Chrome покажет дополнительный запрос подтверждения импорта или доверия, подтвердите его для выбранного `server.crt`.
9. Убедитесь, что в списке **Trusted Certificates** появилась новая запись. В её сведениях имя сайта — **haih.localhost**.

Это действие разрешает браузеру доверять нашему тестовому HTTPS-сайту. Само по себе оно ещё не даёт войти в учётную запись.

Если не получается найти этот раздел через меню, его можно открыть напрямую:

```text
chrome://certificate-manager/localcerts/usercerts
```

Если вместо **Installed by you** открыли **View imported certificates from Linux**, вернитесь назад. Это просмотр сертификатов из системы, а нужная кнопка импорта находится в **Local certificates → Custom → Installed by you → Trusted Certificates**. Запись **DigiNotar Root CA** в разделе **Distrusted Certificates** означает явно заблокированный сертификат; к нашему эксперименту она не относится, менять её не нужно.

### Replacing an older local server CA

If the existing `server.crt` has `CA:TRUE`, record its SHA-256 fingerprint with
`openssl x509 -in docker/traefik/certs/localhost/server.crt -noout -fingerprint -sha256`.
Run `node scripts/setup-certificate-dev.mjs --repair-server-certificate` from the repository root,
then restart the local Traefik container. This replaces the server key and issues a
`CA:FALSE` server certificate. In each browser that trusted the old CA, remove the
trusted entry matching the old fingerprint and import the new server certificate as in step 2.

## Шаг 3. Добавьте свой личный сертификат для входа

1. В том же **Certificate Manager** слева выберите **Your certificates** — ваши сертификаты.
2. Под заголовком **Linux** нажмите **View imported certificates from Linux** — просмотр импортированных сертификатов Linux. Рядом может быть написано **No certificates**: до первого импорта это нормально.
3. Откроется страница **Client certificates from platform**. Нажмите **Import**.
4. В окне выбора файла нажмите **Ctrl+L**, вставьте путь и нажмите **Enter**:

   ```text
   website-template/docker/traefik/certs/localhost/client.p12
   ```

5. Если нужно, нажмите **Open / Открыть**.
6. Chrome попросит пароль файла. Вставьте пароль из **`p12-password`**, который открыли на шаге 1, и подтвердите импорт.
7. Убедитесь, что в списке появился сертификат. Новые файлы используют название **Локальный вход на сайт**. Ранее выпущенный сертификат может отображаться как **Website template local login** или **Local certificate login**; переимпортировать его ради названия не требуется.

Прямой адрес страницы импорта личного сертификата:

```text
chrome://certificate-manager/clientcerts/platformclientcerts
```

Для этого шага нужен именно **`client.p12`**: он содержит и сертификат, и приватный ключ. Файлы `client.crt` и `server.crt` его не заменяют.

### Если импорт прошёл без ошибки, но список остался пустым

В первой версии тестового `client.p12` была ошибка генерации: сертификат имел признак `CA:TRUE`. Chrome импортировал сертификат вместе с ключом, но NSS не включала его в список клиентских сертификатов. Обновление страницы эту проблему не исправляет.

Исправленный файл должен иметь `CA:FALSE` и назначение `TLS Web Client Authentication`. Если файл уже исправлен разработчиком, повторите шаг 3: снова импортируйте **`client.p12` по тому же пути**, используя тот же пароль из **`p12-password`**. Ключ не меняется, поэтому сервер узнает прежнюю учётную запись. Сертификат сайта `server.crt` повторно импортировать не нужно.

Для разработчика: чтобы исправить файлы первой версии, выполните из корня репозитория:

```sh
node scripts/setup-certificate-dev.mjs --repair-client-certificates
```

Команда сохраняет старые сертификаты и `.p12` в файлы с суффиксом `.ca-backup`, перевыпускает клиентские сертификаты с прежними ключами и заново собирает `client.p12` с прежним паролем. Хранилище браузера команда не изменяет. Проверка в отдельной NSS-базе подтвердила: старый сертификат не перечисляется как клиентский, исправленный перечисляется.

## Шаг 4. Войдите на сайт

1. Откройте новую вкладку Chrome: **Ctrl+T**.
2. Вставьте в адресную строку и откройте:

   ```text
   https://haih.localhost:8443/signin
   ```

3. При открытии сайта Chrome может предложить выбрать сертификат. Выберите **Локальный вход на сайт** и нажмите **OK**. Если браузер запомнил выбор, окно может не появиться.
4. Нажмите **Войти по сертификату**. Сайт проверит выбранный ключ и откроет связанный профиль.
5. Если ключ свободен и в базе ещё нет администратора, сайт создаст первого администратора. Если администратор уже есть, появится вопрос о создании второго. Подтверждение сейчас вернёт отказ. Выберите отмену, войдите привычным способом и привяжите ключ в профиле.

### Как привязать ключ к существующему профилю

Откройте **Профиль → Подключённые аккаунты → Сертификаты для входа**. Нажмите **Привязать сертификат**. В профиле появится отпечаток его публичного ключа. Так можно добавить несколько ключей. Попытка привязать занятый ключ возвращает ошибку, в том числе при повторе в своём профиле.

## Шаг 5. Проверьте, что вход выполнен

После входа откройте:

```text
https://haih.localhost:8443/signin
```

Если вход выполнен, приложение перенаправит вас на страницу профиля: `https://haih.localhost:8443/panel/profile`. Для проверки повторного входа сначала выйдите из учётной записи штатной кнопкой выхода, затем повторите шаг 4. Импортировать сертификаты заново не нужно.

## Для разработчика: как устроен эксперимент

Этот эксперимент включается отдельно и добавляет вход по сертификату в существующую форму входа. Авторизация по паролю, через кошелёк и Telegram остаётся доступной. TLS-соединение завершается на Traefik; приложение проверяет **публичный ключ конечного клиентского сертификата** по списку `storage/client-certificate/authorized-keys.pem`. Каждый PEM-блок разрешает предъявителю ключа войти в свой привязанный профиль или создать администратора по описанным выше правилам. Не добавляйте недоверенные ключи.

## Для разработчика: подготовка и запуск

В `docker/.env` задайте параметры клона. Для локальной разработки:

```dotenv
VITE_CLIENT_CERT_LOGIN=true
```

Из корня репозитория выполните:

```sh
node scripts/setup-certificate-dev.mjs
node scripts/configure-certificate-route.mjs --local
docker compose -f docker/compose.yaml -f docker/compose.dev.yaml up -d --build app varnish traefik
```

Compose использует обычную базу и штатные маршруты сайта. Каталог `storage/client-certificate/routes` монтируется отдельным подкаталогом провайдера файлов Traefik. Имя контейнера приложения берётся из имени текущего Compose-проекта. Для своего каталога `TRAEFIK_DYNAMIC_DIR` создайте в нём пустую папку `client-login` под точку монтирования. Подготовка локальных сертификатов сохраняет существующие файлы и создаёт пару для проверки разрешённого и неизвестного ключей.

### Публикация очередного сайта

1. Настройте HTTPS для домена сайта и задайте `VITE_CLIENT_CERT_LOGIN=true` в `docker/.env` перед сборкой.
2. Поместите публичный ключ своего боевого сертификата в `storage/client-certificate/authorized-keys.pem`. Все сайты могут разрешить один и тот же ключ. Приватный ключ хранится у владельца. Для боевого сайта шаг генерации тестовых сертификатов пропускается.
3. При использовании Traefik из шаблона выполните из корня клона `node scripts/configure-certificate-route.mjs --host site.example --entrypoint websec --resolver letsencrypt` (подставьте свой домен, точку входа и resolver). Для уже настроенного серверного сертификата опустите `--resolver`. Команда создаст отдельный для сайта секрет и один дополнительный маршрут входа. Дайте процессу приложения права чтения списка ключей и файла `proxy-secret`.
4. Поднимите сайт штатными `compose.yaml` и `compose.prod.yaml`. Если внешний TLS завершает общий Traefik сервера, установите сгенерированный маршрут именно на нём. Всем HTTPS-маршрутам с явным Host этого домена укажите ту же опцию TLS, что в созданном файле (для другого провайдера конфигурации добавьте суффикс `@file`). В этом случае при генерации задайте `--app <имя-проекта>-app-1`, чтобы внешний прокси обращался к полному имени контейнера нужного клона. Для прокси другого типа требуется эквивалентная проверка владения ключом при TLS и защищённая передача сертификата приложению.
5. Откройте форму входа. Каждый сайт хранит свои связи ключей и пользователей в своей базе.

## Для разработчика: ключи и права доступа

Используйте созданные тестовые сертификаты и ключи только для локальной разработки. Чтобы разрешить собственный сертификат, добавьте его публичный ключ (не приватный) в список разрешённых:

```sh
openssl x509 -in /path/to/client.crt -pubkey -noout >> storage/client-certificate/authorized-keys.pem
```

Изменения списка применяются при следующем входе без перезапуска приложения. Удаление ключа запрещает новые входы по сертификату; уже выданные токены приложения продолжают действовать по существующим правилам сессий, и при необходимости их нужно отзывать отдельно. Привязка использует SHA-256 от SPKI, поэтому перевыпуск сертификата с тем же ключом сохраняет учётную запись. Сертификат должен находиться в пределах своего срока действия. Учётные записи не сопоставляются и не объединяются по субъекту сертификата, CN, электронной почте или текущей учётной записи браузера.

## Граница доверия

Traefik запрашивает клиентский сертификат при подключении к сайту с настройкой `RequestClientCert`. Посетители без сертификата могут войти другими способами. Доверие к центру сертификации не используется как разрешение на вход: даже самоподписанный сертификат может попасть в обработчик проверки, но неизвестный публичный ключ получает ответ 403. Маршрутизатор входа удаляет входящие заголовки идентификации, записывает фактический конечный сертификат TLS-соединения и добавляет 256-битный секрет прокси. Приложение проверяет этот секрет, прежде чем принимать переданный сертификат. Не открывайте доступ к секрету прокси и сгенерированной конфигурации маршрутизации; при переносе на другие окружения сохраняйте порядок этих middleware.

Кнопка входа отправляет JSON-запрос POST на `/api/client-certificate/signin` текущего сайта и получает обычный JWT. При привязке запрос к `/api/client-certificate/link` также передаёт Bearer-токен текущего пользователя. Сервер принимает подтверждение `force: true` только после повторной проверки сертификата и возвращает 403, если sudo уже есть.

## Проверки

Целевые тесты:

```sh
npm test -- server/middleware/clientCertificate/index.test.ts server/database/index.test.ts server/chat/channels.test.ts server/chat/dialogues.test.ts
```

При работающем dev-стеке команда `node scripts/test-certificate-dev.mjs` проверяет открытие сайта без сертификата, вход по разрешённому ключу и отказ при неизвестном ключе или поддельных заголовках. Запускайте на тестовой базе с уже привязанным тестовым ключом либо до создания первого администратора.
